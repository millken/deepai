**让 AI code agent 做多轮 PR review 不跑偏、快速产出，核心是「约束输入 + 结构化输出 + 强制焦点」**。

### 1. 强约束输入（最关键）

不要直接丢整个 PR 或让它自己去逛代码。每次都给它**最小必要上下文**：

- **明确范围**：只 review 这次改动相关的文件/函数，禁止它主动扩展到“顺便看一下周边”。
- **提供 diff + 意图**：把 `git diff`（或 GitHub PR 的 files changed）+ 作者的 description / linked issue 一起给。
- **明确目标**：每次 prompt 开头就写死：
  ```
  你只做 code review，目标是找 bug、安全问题、性能隐患、可读性/可维护性问题。
  禁止：重构建议、风格争论、无关文件、架构大改、教程式解释。
  输出必须按下面模板，不要多余废话。
  ```

多轮时**继承上一轮结论**，而不是重新让它从头看：

```
上一轮 review 结论（已确认）：
1. xxx 问题已确认存在
2. yyy 已修复
3. zzz 待确认

本轮只关注：
- 针对上一轮指出的问题的修复是否正确
- 新增的 diff（贴出来）
禁止重新 review 已确认无问题的部分。
```

### 2. 强制结构化输出模板（防止跑偏）

要求 AI 严格按模板输出，超出模板的内容直接忽略：

```markdown
## Summary
一句话：整体风险等级（Critical / High / Medium / Low）+ 主要问题数量

## Critical / High Issues（必须修）
- [文件:行号] 问题描述 + 为什么是问题 + 建议修复方向（不超过 2 句）

## Medium Issues（建议修）
- ...

## Low / Nit
- ...（可选，控制在 3 条以内）

## Questions for Author
- 需要作者澄清的点（最多 3 个）

## Out of Scope
明确写：本轮不讨论 xxx（防止它自己跑偏）
```

多轮时再加一节：

```markdown
## 上一轮问题状态
- Issue #1：已修复 / 部分修复 / 未修复（说明）
- Issue #2：...
```

### 3. 快速多轮策略

| 轮次 | 目标 | Prompt 重点 |
|------|------|-------------|
| 第1轮 | 找真正严重问题 | 只看 diff + 安全/正确性/崩溃风险，禁止风格和建议重构 |
| 第2轮 | 验证修复 + 新增问题 | 只给「上一轮结论 + 新 diff」，强制对比修复是否有效 |
| 第3轮及以后 | 收敛 | 只允许确认剩余问题是否关闭，禁止再提新建议 |

**技巧**：
- 用「只输出有问题的地方，没有就说 No critical issues」强制它少说话。
- 对大 PR 先让它按文件/模块拆分 review，每次只给一个模块。
- 把 review 规则写成 system prompt 或固定前缀，每次复用。

### 4. 实用 Prompt 模板（可直接复制）

**第1轮**：
```
你是严格的 code reviewer。只做以下任务：

1. 阅读下面的 PR description 和 diff
2. 只找：正确性 bug、安全漏洞、数据竞争、明显性能问题、错误处理缺失
3. 禁止：风格建议、重命名、重构、架构讨论、教程
4. 输出严格按这个模板（不要额外内容）

[模板]

PR Description:
...

Diff:
...
```

**后续轮**：
```
继续上一轮 review。已确认问题：
- ...

本轮只验证这些修复 + 新增 diff 是否引入新问题。
禁止重新讨论已关闭问题。
输出模板同上，并增加「上一轮问题状态」一节。

新 diff：
...
```

### 5. 额外加速手段

- **缩小上下文**：大文件只贴相关函数 + 前后 20 行，而不是整个文件。
- **并行拆分**：大 PR 拆成多个独立 review 请求（按模块/文件），最后人工汇总。
- **工具辅助**：先用 linter / static analysis 结果作为输入，让 AI 只做「深度逻辑」部分。
- **停止条件**：明确告诉它「如果连续两轮没有 Critical/High，就输出 Done」。

按上面做，通常 2–3 轮就能把真正重要的问题收敛完，而且不会越 review 越发散。关键是**永远不要让它自由发挥**，每次都用「范围 + 模板 + 继承」把它钉死。
