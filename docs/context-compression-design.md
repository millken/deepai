# DeepAI 上下文分层压缩架构设计

- **状态**：待 Review
- **日期**：2026-08-01
- **数据基础**：`~/.deepai-metrics.jsonl`（3598 条记录，~1642 会话 / 1794 turns / 1866 次工具调用）

---

## 1. 背景与问题

Agent 会话的上下文随工具调用累积持续增长。现有压缩机制（T1 ToolResultBudgets + 单阈值 MinContextPressure）存在三个问题：

1. **阈值触发无迟滞**：单一压力阈值导致"每轮压一点"的抖动，压缩成本高、cache 频繁失效；
2. **预算一刀切**：所有工具共用一个 age budget，与实际大小分布不匹配；
3. **大结果无源头防护**：单个超大工具结果（grep 471KB、git_diff 251KB）直接进入上下文，事后再压缩代价高。

### 1.1 实测数据（修正版）

对 3598 条记录的全量分位数分析，**修正了此前报告中的误读**：

| 工具 | 调用次数 | p50 | p90 | p99 | max | 结论 |
|---|---|---|---|---|---|---|
| read_file | 530 | 1.3KB | 5.2KB | 13.3KB | 34KB | 中等，最新读取需重点保护 |
| bash | 522 | 277B | 1.2KB | 4.3KB | 5.5KB | 小 |
| edit_file / write_file | 446 | ~55B | ~90B | ~105B | 105B | 极小，仅确认信息，可即时折叠 |
| grep | 66 | 450B | 3.5KB | 168KB | 471KB | **尾部风险**（非普遍风险） |
| git_diff | 16 | **15.6KB** | 63KB | 225KB | 251KB | **系统性大结果**（中位数即超预算） |
| web_fetch | 51 | 4.5KB | 10KB | 17.5KB | 20KB | 中等偏大且稳定 |
| **全局** | 1866 | 310B | 3.1KB | 12.9KB | 471KB | 尾部驱动 |

关键事实：

- **>8KB 的结果仅占 2.4%，但占工具总字节的 47%**（1.4MB / 3.0MB）。预算设计必须针对尾部，而非均值。
- **~1642 会话 / 1794 turns，平均 1.09 turn/会话**：绝大多数会话是 1-2 轮的超短会话。此前"Turn1→5 tool_fraction 上升趋势"只是长尾个例。
- **input_tokens 1792/1794 全为 0**：provider 未回传 usage，当前所有占比分析基于 bytes，不是 tokens。

### 1.2 两个客户群，两套手段

| 群体 | 占比 | 成本构成 | 优化手段 |
|---|---|---|---|
| 短会话（1-2 轮） | 绝大多数 | 固定开销（schema 37.8% + system 23.9%） | prompt caching、schema 静态子集 |
| 长会话（10+ 轮） | 少数但 context 可达 1.15MB | 工具结果累积（tool_bytes 35.7% 且递增） | 本文档的分层压缩 |

**推论**：压缩系统主要为长会话服务；短会话的省钱答案是缓存，不是压缩。两者不要混为一谈。

## 2. 设计目标与非目标

### 目标

1. 长会话上下文水位受控，不触顶（context overflow = 会话失败）；
2. 压缩代价可接受：不引发显著重读、不丢失行动依赖信息（路径/决策/错误）；
3. 缓存友好：压缩操作最小化 KV cache / prompt cache 失效；
4. 可度量：所有压力判断基于 tokens（或校准估算），效果可离线回放评估。

### 非目标

- 不追求极限压缩率（过度压缩 → 重读率上升，总 token 反而更高）；
- 不改变短会话（1-2 轮）的任何行为；
- 不在本轮解决 system prompt 内容精简（独立议题）。

---

## 3. 总体架构

四层防护 + 双阈值迟滞触发：

```
工具输出 ──> [L0 源头防护] ──> 进入上下文
                                    │
                              每轮结束测量压力 P
                                    │
              ┌─────────────────────┼──────────────────────┐
         P < 0.35              0.35 ≤ P < 0.55         0.55 ≤ P < 0.90      P ≥ 0.90
              │                     │                      │                  │
           不动作            [L1 确定性压缩]          [L2 语义摘要]      [L3 会话重建]
           （常态）          去重/折叠/掐头留尾        结构化摘要旧轮次     handoff 重开会话
                                    │                      │
                              压缩至 P ≤ 0.25 即停（迟滞目标）
```

核心原则：

- **越早的层越便宜、越无损**：能在源头截断的，不留到事后压缩；能用确定性规则压缩的，不动用 LLM 摘要；
- **越晚的层越贵、越有损**：L2/L3 是兜底，不是常态；
- **触发有迟滞**：压缩到目标水位 0.25 即停，避免在阈值附近反复抖动。

---

## 4. 压力定义与触发机制

### 4.1 压力（Pressure）定义

```
P = context_tokens / effective_window
effective_window = model_window - reserved_output_tokens
```

- `context_tokens` 取值优先级：**provider 回传 usage > tokenizer 实测 > bytes 校准估算**（见 §7）；
- `reserved_output_tokens` 建议为 model_window 的 10-15%（待 review，见 §12 Q1）。

### 4.2 阈值与迟滞

| 参数 | 推荐值 | 含义 |
|---|---|---|
| P_soft | 0.35 | 触发 L1 确定性压缩（无 LLM 调用，低损） |
| P_hard | 0.55 | 触发 L2 语义摘要（有 LLM 调用，有损） |
| P_crit | 0.90 | 触发 L3 会话重建（最后防线） |
| P_target | 0.25 | 每次压缩到此水位即停（迟滞下界） |

**为什么不是简单把 MinContextPressure 从 0.4 降到 0.3**：

- 单阈值意味着越过线就压，下一轮又越线又压——每次压缩都伴随 cache 失效和（可能的）摘要调用成本；
- "固定开销占 61.7%"是当前 context 快照的构成占比，不是占窗口的水位，不能作为降阈值的依据；
- 双阈值把"便宜的压缩"和"贵的压缩"分流：0.35-0.55 区间只做无 LLM 成本的 L1，把昂贵的 L2 推迟到真正必要时。

### 4.3 触发时机

- **只在 turn 边界触发**，不在 mid-turn 压缩：
  - mid-turn 改写历史会破坏当前推理链的连贯性；
  - turn 边界是 cache 前缀变化的自然点，损失最小；
- **每轮最多压缩一次**：L1 后重测压力，仍 >P_hard 才升 L2；一次到位压至 P_target，不做多轮增量小压缩。

## 5. 各层详细设计

### 5.1 L0 源头防护（常驻，不占压缩触发）

目标：让超大结果**根本不进上下文**。这是 ROI 最高的一层——47% 的工具字节来自 2.4% 的大结果。

| 手段 | 适用 | 行为 |
|---|---|---|
| 结果数/行数上限 | grep | `max_results` + `head_limit`，默认截断并标注"已截断，共 N 行" |
| 降级输出 | git_diff | **默认输出 `--stat`**（文件清单+行数统计），agent 需要细节时按文件 drill-down |
| 掐头留尾 | bash/web_fetch | 超上限保留 head 70% + tail 30%，中间标注省略 |
| 超限落盘 | 全部 | 单结果 > `OFFLOAD_THRESHOLD`（建议 24KB）时写入 `~/.deepai/offload/<hash>.txt`，上下文内只留引用+摘要+首尾各 50 行 |

要点：

- **git_diff 不要用"超阈值询问用户"策略**——在自治循环里这是反模式，会卡住整个流程。`--stat` + drill-down 是无交互的等价方案；
- offload 落盘同时解决了"压缩后需要回溯"的问题：被截断的内容有完整副本可查（见 §12 Q3 清理策略）；
- read_file 侧配套鼓励分页/行范围读取（工具描述中引导）。

### 5.2 L1 确定性压缩（软压缩，P ≥ 0.35）

无 LLM 调用、规则驱动、低损。按顺序执行，压到 P ≤ 0.25 即停：

1. **去重**：相同 `args_hash` 的重复工具结果（如反复读同一文件）只保留最新一份，旧份替换为占位引用；
2. **即时折叠**：edit_file / write_file 类确认消息（实测 p99 < 105B，几乎无信息）折叠为单行标记；这类结果甚至可不占 age-1 预算；
3. **按工具差异化 budget 掐头留尾**：超龄结果按 §5.4 预算表截断，head 70% / tail 30%。

**保护清单（任何层都不得触碰）**：

- 最近一条用户消息；
- 当前 plan / todo 状态；
- 未解决的错误信息；
- 最近 N=2 轮的工具结果（最新读取是最可能马上被 edit 使用的，截它最易引发重读——重读一次的成本 > 省下的 token）。

### 5.3 L2 语义摘要（硬压缩，P ≥ 0.55）

对 age ≥ 3 的轮次生成**结构化摘要**（不是字节级截断）：

```json
{
  "files_modified": ["src/foo.ts", "docs/bar.md"],
  "key_decisions": ["采用双阈值迟滞方案，放弃单阈值"],
  "unresolved_errors": ["zig_check 报错未修复"],
  "user_requirements": ["预算表按工具差异化"],
  "next_steps": ["实现 L0 offload"]
}
```

- 摘要模型可用小模型（成本敏感）；100B 级别的字节截断会丢失路径/决策/错误这些行动依赖信息，**明确反对此前 {2:300, 4:100} 的 T4 配置**；
- 被摘要的原始内容整体落盘，摘要中保留 offload 引用；
- 保护清单同样适用。

### 5.4 按工具差异化的 Age Budget（基于实测分位数）

| 工具 | 依据（p90/p99） | age 1 | age 2 | age 3+ |
|---|---|---|---|---|
| read_file | 5.2KB / 13.3KB | **8192**（保留最新读取，防重读） | 2048 | 300 |
| bash | 1.2KB / 4.3KB | 4096 | 1024 | 300 |
| edit_file / write_file | 90B / 105B | 300（或即时折叠） | 300 | 300 |
| grep | 3.5KB / 168KB | 4096 + L0 源头截断 | 1024 | 300 |
| git_diff | 63KB / 225KB | 2048（L0 已 --stat 化） | 1024 | 300 |
| web_fetch | 10KB / 17.5KB | 8192 | 2048 | 300 |
| 其他/默认 | — | 4096 | 1024 | 300 |

说明：此前"age-1 统一 8KB → 4KB"的建议方向正确（全局 p90 仅 3.1KB），但一刀切 4KB 会截断 10%+ 的最新 read_file，必须按工具分开。

### 5.5 L3 会话重建（P ≥ 0.90）

生成 handoff 摘要（结构化 schema 同 L2，另附关键文件清单与 offload 引用），开启新会话携带摘要继续。

- 是否自动执行还是需用户确认——待 review（§12 Q4）；
- 这是最后防线：到达 0.90 说明 L0-L2 均失效（如单个任务本身需求超大上下文），此时保会话连续性优先于保细节。

## 6. 缓存友好性设计

压缩的隐性成本是 KV cache / prompt cache 失效。约束：

1. **工具列表在会话开始时确定，中途不增删**——schema 懒加载/动态加载会破坏缓存前缀，省下的 schema token 大概率抵不上 cache 全量失效。如需精简，按任务类型选定**静态子集**（会话级）；
2. **压缩批量发生在 turn 边界**（见 §4.3），一轮一次；
3. 压缩点之前的历史尽量保持 append-only，让稳定前缀尽可能长地存活；
4. system prompt + schema 作为最前前缀，任何版本迭代都要意识到这会全量失效缓存（短会话群体的主要成本来源）。

## 7. Token 计量与校准（地基工程，最高优先级）

当前 input_tokens 1792/1794 全为 0，所有压力判断基于 bytes——**阈值都是猜的**。修复路径：

1. **provider usage**：OpenAI 兼容接口开启 `stream_options.include_usage`；Anthropic 解析 `message_delta` 中的 usage；
2. **拿不到 usage 时**：接入模型对应 tokenizer 实测；
3. **兜底**：bytes→tokens 校准系数。用已有样本做回归（中英混合场景比例差异大：英文约 3.5-4 bytes/token，中文 UTF-8 约 2 bytes/token），按内容类型分别拟合，定期复校。

验收标准：任意 turn 的 tokens 估算与 provider 实测（可得时）误差 < 10%。

## 8. 评估方案（离线 Replay）

已有 3598 条记录就是最好的评估集。**参数没有回放数据支撑，调的都是手感。**

### 8.1 方法

回放历史会话，对候选参数组合（P_soft × P_hard × budget 表）模拟压缩行为，对比：

| 指标 | 含义 | 期望 |
|---|---|---|
| context 水位曲线 | 峰值/均值 | 峰值 < P_hard，不触顶 |
| 压缩触发频率 | L1/L2 各多少次 | L2 稀少（< 5% turns） |
| 压缩成本 | 摘要 LLM 的 token 消耗 | < 节省量的 20% |
| **重读率** | read_file 重复读取同一文件的比例 | 不显著高于无压缩基线 |
| cache 命中率 | （若 provider 返回 cached tokens） | 短会话 > 80% |

**重读率是过度压缩的直接证据**：文件被压掉 → agent 不得不重读 → 总 token 不降反升。

### 8.2 前置条件：metrics 增强

当前 tool 记录只有 `tool_name` 和 `result_bytes`，无法统计重读率。需新增：

- `args_hash`（工具参数哈希，识别重复调用）；
- `path`（文件类工具的目标路径）；
- `offloaded: bool`（是否触发落盘）；
- provider usage 字段（见 §7）。

## 9. 推荐配置汇总

```yaml
pressure:
  soft: 0.35        # L1 触发
  hard: 0.55        # L2 触发
  crit: 0.90        # L3 触发
  target: 0.25      # 迟滞下界，压到即停
  reserved_output_ratio: 0.12

l0_source_guard:
  offload_threshold_bytes: 24576
  offload_dir: ~/.deepai/offload/
  grep: { max_results: 200, head_limit: 100 }
  git_diff: { default: "--stat", drill_down: true }
  truncate: { head_ratio: 0.7, tail_ratio: 0.3 }

l1_budgets_bytes:    # 见 §5.4，按工具 × age
  read_file:  { 1: 8192, 2: 2048, 3: 300 }
  bash:       { 1: 4096, 2: 1024, 3: 300 }
  edit_file:  { 1: 300,  2: 300,  3: 300 }
  write_file: { 1: 300,  2: 300,  3: 300 }
  grep:       { 1: 4096, 2: 1024, 3: 300 }
  git_diff:   { 1: 2048, 2: 1024, 3: 300 }
  web_fetch:  { 1: 8192, 2: 2048, 3: 300 }
  default:    { 1: 4096, 2: 1024, 3: 300 }

protection:
  recent_turns: 2
  never_compress: [last_user_message, current_plan, unresolved_errors]
```

## 10. 实施路径

| 里程碑 | 内容 | 依赖 |
|---|---|---|
| M1 | token 计量修复 + metrics 增强（args_hash/path/usage） | 无，**最优先** |
| M2 | L0 源头防护（grep 上限 / git_diff --stat / offload 落盘） | 无，ROI 最高 |
| M3 | L1 + 双阈值迟滞 + 差异化预算表 | M1（压力要可信） |
| M4 | 离线 replay 评估 + 参数扫描，校准 §9 配置 | M1，数据要够 |
| M5 | L2 结构化语义摘要 | M4 验证 L1 不足后 |
| M6 | L3 会话重建 | M5 |

原则：先用便宜的层拿到收益，用 replay 数据证明不足后再上贵的层。

## 11. 风险与权衡

| 风险 | 缓解 |
|---|---|
| bytes 估算偏差导致误触发 | M1 修复计量；阈值留有迟滞带 |
| 摘要丢失行动依赖信息 | 结构化 schema + 保护清单 + offload 可回溯 |
| 摘要 LLM 成本倒挂（压缩比不压还贵） | 小模型摘要 + 迟滞减少频次 + replay 监控压缩成本占比 |
| 压缩引发 cache 失效毛刺 | turn 边界批量压缩；静态工具子集 |
| 过度压缩引发重读 | read_file age-1 保护 + 重读率监控告警 |
